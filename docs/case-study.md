# 实战案例：一次跨目录的大规模迁移

> 这是本文档集配套的真实案例（已脱敏）。它回答两个问题：
> ① 这套方法论真的能扛住多大的迁移？② 哪些地方最容易出事？

---

## 一、背景

项目散落在 `~/Documents/` 下的多个分类目录（按 AI 工具分的 `xxx/`、按来源分的其它目录…），约 **25 个项目目录、8GB+**。目标是按"项目属性"而非"用什么工具开发"重新组织到 `~/Projects/`，并给目录起"中文+英文"的可读名字。

原分类维度是"用哪个 AI 工具"——但实际开发中这些工具是混用的，所以这个分类维度本身是错的。

**目标结构**：
```
~/Projects/
├── <活跃项目平铺>          日常在用的
├── opensource/            开源项目（有自己的更新节奏）
├── archive/               冷却项目（冻结，不改造）
└── sandbox/               一次性实验（随时可删）
```

## 二、规模与风险画像

| 维度 | 数量 | 说明 |
|---|---|---|
| 项目目录 | 25 个 | 分 3 批迁移 + 后续改名轮 |
| git 仓库 | 21 个 | 搬家对 git 完全无影响（实测零丢失） |
| **硬绑定服务** | 2 个 | 一个 launchd 常驻服务、一个 5 容器的 Docker 栈 |
| **Python venv** | 6 个 | 需修正 shebang 或重建 |
| **符号链接** | 10+ 条 | 用户级 skill 链接 + 项目间链接 |
| 写死路径的文件 | 200+ 个 | 大多是文档，少量是会执行的代码 |
| **AI 工具绑定** | 4 个工具 / 30+ 记忆目录 | 本指南的核心对象 |
| 历史会话 | 467 个 | 需要迁移归属标签 |
| 未提交改动 | 最多的仓库 75 处 | 搬家前 commit 留快照 |

## 三、发现的关键事实（决定了方案形态）

1. **会话内容与路径解耦** → 迁移永远不会丢数据，最坏可回滚 → 这是整个方案敢做的前提。
2. **绝大多数"绑定"其实只有 2 处**（一个 plist 的一行 + 一个启动脚本的一行）→ 看起来吓人的"常驻服务"，修复成本是分钟级。
3. **白名单代码本来就已经支持新路径** → 盘点时看报错信息误判为"需要改代码"，读源码后推翻了 → **证据优先的价值**。
4. **一个"从未迁移"的孤儿记忆**（哈希对应的是 3 个月前的旧路径）→ 只有全量比对哈希才能发现，不是本次搬家造成的。
5. **iCloud 同步是关闭的** → 排除了一大类"搬运会触发云端重传"的风险。

## 四、实际修复工作量

| 批次 | 处理内容 | 耗时 |
|---|---|---|
| 批次 1（低风险） | 7 个项目搬迁 + 路径改造 + 22 个测试验证 | ~30 min |
| ZCode 记忆键迁移 | 3 个记忆目录改名 | ~10 min |
| 批次 2-3 | 11 个项目 + 2 个 venv 复活 + 死服务卸载 + 死链修复 | ~40 min |
| 服务窗口（Docker） | `down → 搬 → up` 5 容器恢复 healthy | ~5 min |
| 服务窗口（launchd） | 停 → 搬 → 修 2 行配置 → 起 → curl 验证 | ~5 min |
| 改名轮（11 项 + 2 个数据库） | 由 AI Agent 执行，我做两轮审查修复 | ~40 min |

**总计约 2 小时**（含全部检查、验证、文档沉淀）。

## 五、出过问题的地方（按严重度）

### 5.1 差点漏掉的一类：用户级软链

前三批都做完了、功能都验证通过了，才发现 `~/.agents/skills/` 里 4 条软链全断——因为它们指向项目内的绝对路径。这类链接**不在项目目录里**，扫项目永远扫不到。

> 这是本案例最大的教训：**项目内的引用只是问题的一半**。清单里的 7 项盲区，每一项都真实坏过一次。

### 5.2 一个判断错误：venv 不用重建

第一版方案写的是"venv 需要重建，约 5 分钟/个"。实测发现同机迁移只需修正 shebang（`sed` 一条命令）即可复活，**秒级完成**。

> 推广：清单类操作前先验证一遍，能把"预估成本"和"实际成本"的差距消掉。

### 5.3 一个冤枉：一个"服务在坏"其实是路径失联

静态站点预览服务搬家后返回 404，第一反应是"服务坏了"。逐步排查发现：进程活着、文件完好、端口在听——只是旧进程持有的是**改名之前的目录句柄**。重启即好。

### 5.4 改名的连锁反应（第二轮审查才发现）

11 个项目改名之后，第一轮修复了软链/服务/文档，但二轮深审又挖出：
- 一个脚本里的**代码级路径兜底值**（下次跑 ASR 才会暴露）；
- 有个别的工具的记忆目录没跟着改名（改名操作只处理了 ZCode 这层）；
- 4 个失效的权限缓存键。

> 推广：**改名的影响面比搬家大**，因为改名还会打断"名字 ↔ 工具内部标识"的映射关系。改名前后各扫一轮。

## 六、可复用的决策原则

这次形成的几条判断标准（写进了记忆，也写进了本仓库的 checklist）：

| 情况 | 决定 | 理由 |
|---|---|---|
| 旧路径引用在**活跃项目**里 | 立刻改 | 收益当天兑现（AI 每天读），且有测试兜底 |
| 在**一次性脚本**里 | 用到再改 | 提前改无法验证，反而埋雷；不用则零影响 |
| 在 **sandbox** 里 | 不改 | 随时可删，投资无意义 |
| 在 **archive** 里 | 不改 | 旧路径是"当时事实"的一部分，冻结即价值 |
| 在**测试数据/注释**里 | 不改 | 那是功能语义，改了破坏测试 |
| **删除**操作 | 一律进废纸篓 | 不可逆操作必须有退路 |

## 七、验收标准（最终采用了这些）

1. **git 改动数零漂移** —— 每个仓库迁移前后的未提交改动数完全一致；
2. **全量测试通过** —— 620 passed（含 27 subtests），这是最有说服力的一条；
3. **服务实测**：API `curl` 有响应、容器 healthy、静态站 HTTP 200 且字节数与迁移前基线一致；
4. **AI 工具实测**：在新路径打开工作区，问"你的记忆文件里有什么" —— 能读出 30+ 条记忆才算成功；
5. **全环境软链断链 = 0**。

## 八、给读者的 takeaway

- 迁移 25 个项目、4 个 AI 工具、2 个服务，**真正的风险点不到 10 个**，其余都是纸面复杂度；
- 但那 10 个风险点里，**没有一个能靠"盯着项目目录"发现**——全都在项目外面；
- 所以方法论的核心不是任何一条命令，而是那份**清单**。
